# Setup Canvas
Read this skill's [account-access reference](references/account-access.md) before configuring anything. This setup owns the Canvas configuration, credential storage and provider runtime (`scripts/canvas_auth.py`) that `use-canvas` loads. [use-canvas](../use-canvas/SKILL.md) supplies course listing, `verify`, exports, downloads and operation history; supported course-content writes use a separate preview, approval and execution gate. Setup changes no course content. Optional credential renewal creates only a successor token for the confirmed user under separate explicit authorization; read [token renewal](references/token-renewal.md) first.

Canvas documents manual tokens for testing one's own application; applications used by others require OAuth with an administrator-issued developer key. This runtime implements the personal-token testing flow and optional successor-token renewal, not OAuth onboarding. Do not present this as completed general-user authentication. See the [official authentication guidance](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth).

## Runtime
Python 3.11 or later with only its standard library; no Bash or third-party package is needed. If uv is missing, follow the [official installer](https://docs.astral.sh/uv/getting-started/installation/) within setup authorization; uv can provision a compatible Python for this folder's manifest. From the collection root:
```sh
uv run --project setup-canvas python setup-canvas/scripts/canvas_auth.py --help
```
A compatible `python3` can run the script directly. Time-zone handling uses the system time-zone database; native Windows needs the `tzdata` package and is unverified. macOS offline checks pass; fresh Linux and Windows bootstrap are not yet verified.

## Connect an account
1. Explain the trade-off first. A Canvas personal access token is password-equivalent, cannot be scoped without an administrator-configured developer key, and lets whoever holds the file act as the user across the whole instance. Agent Hands calls only the endpoints its Canvas skills document, but the token itself is not limited to them.
2. Ask the user to check their institution's published policy on personal tokens and third-party tools. Setup cannot determine policy, and a visible button is not permission. If policy forbids it, stop and say so; do not offer browser sessions or scraping as a workaround.
3. Ask the user to open `https://<their instance>/profile/settings` in their own browser and say whether **New Access Token** appears under Approved Integrations. Administrators can turn creation off (Canvas documents a *Limit Personal Access Token Creation* setting, and a separate student and observer restriction exists), so absence is a normal outcome: report `token_creation_unavailable` and stop. Look at that page yourself only with explicit browser approval, and never press the button.
4. If creation is available and permitted, the user creates the initial token themselves, with a purpose label and an expiry date, and pastes it into the ignored `.env` in their own editor. Never ask for the token in chat, in a command argument or in a tracked file. The initial setup does not create, regenerate or delete a token through the API. Later explicitly authorized successor-token renewal uses only its bounded procedure.
5. In this setup folder, confirm `git check-ignore` reports `.env` and `canvas-accounts.json` as ignored, then copy `.env.example` and `canvas-accounts.example.json` only where the real files are absent. Preserve existing accounts. Set owner-only permissions on `.env` (`chmod 600`). Fill in the alias, the instance origin as `base_url`, `token_env`, and the expiry the user chose as `token_expires`; leave `user_id` empty.
6. Run `check ALIAS` (no network) and fix anything it reports.
7. With the user's permission for one read, run `whoami ALIAS`. It prints the Canvas user ID, display name and time zone, never email or login. When the user confirms it is their account, record the printed ID as `user_id`. From then on a different token identity stops every command.
8. Record course selection as the user directs. A course's ID is the number in its web address (`https://example.instructure.com/courses/123`). Selection decides what gets exported; it is not a write restriction and does not narrow the token.

Report local readiness, the identity read and anything still unverified separately. Initial setup performs no test write; a separately requested credential-renewal test uses the bounded renewal procedure and authorizes no course-content change.

## Reconnect, rotate or disconnect
A `token_rejected` error means Canvas refused the token: it expired, was revoked or was regenerated. The user creates or regenerates one in their profile settings (if still permitted), replaces the `.env` value and updates `token_expires`; `whoami` must then match the recorded `user_id`. A changed instance address updates `base_url` only after the user confirms it, followed by `whoami`. To disconnect, the user deletes the token in Canvas, then remove the `.env` value and the alias. Never move or rewrite another account's entry.

For requested automatic renewal, use [token renewal](references/token-renewal.md). `token-status ALIAS` reads only the configured token's metadata. `token-renew ALIAS --enable-auto` previews a successor and the opt-in policy; apply only after approval with `--execute --expect HASH`. Preserve existing approval within its actual scope. After enablement, normal `use-canvas` calls renew near expiry entirely in Python. An idle connection can still expire; no background job is installed. Institution denial, unresolved requests and expired credentials require attention rather than access workarounds.

## Account access and shared runtime
This setup skill owns the provider runtime, examples and tests that `use-canvas` loads: configuration parsing, the token's origin-only transport, pagination, throttling back-off, error kinds and the identity check. Normal operations do not require rerunning setup. Keep credential establishment separate from permission for each Canvas action, and preserve existing user approval within its stated scope.

## Optional global discovery
Use the packaged `scripts/link-skills.py` for requested global discovery; it selects exactly `setup-canvas` and `use-canvas`. Read [global skill links](../setup-agent-hands/references/global-skill-links.md), inspect the existing client location and preserve it with `--skills-dir ABSOLUTE-PATH` for a single client when needed. From the collection root, `python3 setup-canvas/scripts/link-skills.py --client codex --client claude` previews both clients; add `--execute` within the requested installation scope. The installer uses Python 3.9+ with the standard library and requires the sibling `setup-agent-hands/scripts/skill_links.py`; Canvas commands still require Python 3.11+. It does not configure credentials or register an MCP server. Resolve an installed skill link to its checkout before using collection-root examples, and keep the setup/use folders and shared helper together. Direct checkout use needs no links.

## Offline checks
From the collection root, `uv run --project setup-canvas python -m unittest discover -s setup-canvas/tests -p 'test_*.py'` runs all 40 configuration, transport and token-renewal tests. They cover literal account configuration, the local check, credential isolation, pagination, redirects, throttling, error classification, identity, renewal gating and interrupted-save recovery, with the real HTTP transport exercised against a loopback server. `python3 -m unittest discover -s setup-agent-hands/tests -p 'test_skill_links.py'` runs the 16 shared installer checks, including the Canvas selection. A tracked-files-only Canvas package has also passed preview/install/idempotence for both clients and CLI help through its packaged paths. Filesystem and entrypoint checks do not prove discovery in a fresh client conversation, institution policy or access on another instance.
