# Isolated Canvas test-cluster smoke tests
Read [use-canvas](../SKILL.md) and the [write guide](writes.md). This workflow prepares explicitly authorized tests on an exact hosted `https://NAME.test.instructure.com` origin in one unpublished course. Production, beta, lookalike hosts, other courses and arbitrary user impersonation refuse. The ordinary fifteen write commands retain their existing bounds; `create-test-discussion` is an additional fixture helper requiring a signed test session. No general roster, enrollment, grading, user-deletion or discussion-authoring interface is added.

## Establish the test connection
Use `setup-canvas` with a separate explicitly selected account/origin. A credential that works on production may be rejected on test; verify an existing credential before requiring a new one. A new initial test credential is created by the user in the test site's own profile settings. Keep both origin routing and credentials private, preserve the production profile and do not silently enable renewal on another profile. The user's confirmed identity and course selection are still required.

The live file-submission test exposed a cleanup limit: Canvas protects files associated with submission history, even after their assignment is removed. Direct attachment deletion is insufficient. Do not start another learner-upload smoke cycle until a separately approved cleanup route is implemented and verified; do not promise a full rollback from the current direct-delete workflow. The normal learner submission command remains available outside this disposable-test workflow.

Instructure documents that outgoing [test-environment notifications cannot be sent](https://community.instructure.com/en/kb/articles/661149-unknown). Confirm the intended test installation with the user before connecting. This workflow uses only native Canvas content, with no external applications or LTI launches. Test data can be overwritten by the institution's refresh; changed or missing baselines stop execution. A test result does not establish production notification behavior or compatibility at another institution.

## Signed preparation and learner access
From the collection root, with an authorized test account:
```sh
uv run --project use-canvas python use-canvas/scripts/canvas.py test-session example-test --course 123 --json
uv run --project use-canvas python use-canvas/scripts/canvas.py prepare-test-learner example-test --session SESSION --json
uv run --project use-canvas python use-canvas/scripts/canvas.py prepare-test-learner example-test --session SESSION --execute --expect HASH --json
```
`test-session` sends no mutations. It records complete course inventories/order, separate announcement/discussion inventories, existing sections and only Test Student enrollment identities. It uses the same owner-only signed store as ordinary smoke sessions. Existing folders and assignment groups must be chosen explicitly. All ordinary required delete permissions, topic moderation, Student View and page-update permissions must be explicitly true.

The learner is Canvas's built-in Test Student, proved by the selected course's `StudentViewEnrollment` records. No learner ID argument or alternate user-selection flag is exposed. An existing Test Student is reused and its enrollment/files are preserved. If absent, preparation requires explicit `use_student_view` permission, existing sections, a preview and its fresh hash. The [student-view endpoint](https://developerdocs.instructure.com/services/canvas/resources/courses#method.courses.student_view_student) is a GET that creates a user/enrollments: it is journaled as a mutation before sending, sent once without ordinary read retries, and returned identities are signed before later verification. Each new enrollment must match an existing section and receives a cleanup receipt.

The learner client uses the existing instructor credential and only the signed Test Student via `as_user_id`. It verifies the returned self ID and course identity, and permits only identity/course reads, the learner's file inventory and paths belonging to recorded fixtures. It never accesses arbitrary users or another course. Test Student profiles are unsupported: the course supplies the time zone without a profile request. Upstream [User.can_masquerade?](https://github.com/instructure/canvas-lms/blob/master/app/models/user.rb) explicitly handles the fake student, and [Enrollment.can_be_deleted_by](https://github.com/instructure/canvas-lms/blob/master/app/models/enrollment.rb) requires Student View permission for its enrollment removal. Institution-specific access still requires live verification.

For interrupted preparation, `test-status ALIAS --session SESSION --json` reports bounded identity/access results and signed receipt state without mutations. `verify-test-learner ALIAS --session SESSION --json` can finish only an acknowledged new learner with its exact signed response ID and enrollment receipts, one durable pending marker, unchanged course/section baseline, successful learner identity and an empty initial personal-file inventory. A missing response ID, another learner, an unrecorded file or changed enrollment refuses. It never creates another learner or guesses ownership by a name.

## Fixture and learner writes
Attach every action to `--test-session SESSION`; ordinary `--smoke-session` remains separate. Names and uploaded submission filenames use the returned prefix. Review the actual bodies, targets, schedule, publication and cleanup in conversation before the content cycle. Each action rebuilds its own preview immediately before execution with `--execute --expect HASH`.

A scheduled test announcement can have `posted_at` equal to creation time while its future `delayed_post_at` remains intact. Editing that exact owned announcement requires the unchanged signed receipt and a delay still more than one day ahead; the ordinary announcement guard remains unchanged. The topic inventory omits the `only_announcements` parameter for discussions because Canvas treats the presence of a false value as an announcement filter.

Supported fixtures and actions:
- Unpublished page creation/editing and an actual `revert-page` to a revision recorded for that same test page. The revert checks body, title, URL and the new revision. A front page or published page refuses.
- Announcement creation/editing, always scheduled more than one day ahead. `--notify-course` is still required for creation because the normal endpoint can notify; the test host restriction supplies the documented delivery boundary.
- A new published zero-point assignment in an explicitly selected existing group, accepting only text, URL and/or upload submissions, with no dates or overrides. The course remains unpublished. No existing assignment is adopted.
- `create-test-discussion --course ID --test-session SESSION --title 'PREFIX discussion' --body-file PATH` creates a published, ungraded threaded topic for the test only.
- `submit-assignment`, `comment-submission` and `reply-discussion` on the recorded fixtures, automatically using the verified Test Student. A nested reply must reference a recorded entry in the same topic. One explicitly tracked attachment per submission action is supported; there is no fixed byte-size cap. Upload bytes are re-downloaded and checked before cleanup.

Publication of the two learner fixtures is explicit; course publication, notifications on page/assignment updates, front-page changes, duplicates, overwrites, unrelated edits and module moves remain excluded. Submission attempts are real attempts within the test copy. Their eventual cleanup removes the newly created assignment's active parent, rather than claiming an independent withdrawal operation. A foreign submission/comment/reply, grading, changed fixture or unexpected inventory stops cleanup before a destructive request.

The first submission changes the assignment's documented [`unpublishable`](https://developerdocs.instructure.com/services/canvas/resources/assignments) flag from true to false along with submission/grading counts. These fields are tracked as parent metadata. If a first text POST was durably verified but an older signed parent proof omitted that flag, `verify-test-submission ALIAS --session SESSION --preview-file ORIGINAL-SUBMISSION-PREVIEW.json --json` can reconcile the receipt with zero Canvas mutations. It requires the exact signed pre-state, reconstructed original preview fingerprint, one verified POST, matching teacher/learner readback, one ungraded first text attempt within the original operation's timestamps, no comments/attachments/earlier learner receipts, and reconstruction of the entire prior parent fingerprint after reversing only the recorded metadata and true-to-false flag. It never resubmits, adopts an unknown response or overrides another changed field. `test-status --inspect-owned` exposes bounded receipt/metadata diagnostics without bodies or credentials.

Upload confirmation may name `/api/v1/files/ID` directly rather than `/create_success`. The test workflow signs that exact response ID before allowing confirmation. For a legacy interruption after the storage POST and before any confirmation/submission, `verify-test-upload ALIAS --session SESSION --preview-file ORIGINAL-UPLOAD-PREVIEW.json --json` can establish one already active upload through reads only. This narrow recovery requires a newly created Test Student with an empty signed file baseline, exactly one new personal file, reconstructed original preview/hash and protocol markers, unchanged assignment/submission receipts, exact local and downloaded bytes, matching name/type/size, and creation/update timestamps within the original upload request interval. Extra files, prior attachment receipts, existing learners, a sent confirmation/submission or any differing content refuse. It records observed file presence and resolves the storage marker without claiming a confirmation was sent. The recorded file can then be freshly previewed with `submit-assignment --test-session SESSION --test-attachment ID`; this sends one submission and no upload. Ordinary commands cannot reuse an arbitrary attachment through this option.

Canvas can advance a submission attachment's `updated_at` after the submission is verified. Test attachment receipts exclude only that timestamp, including its embedded copy in the submission; modified time, other metadata and downloaded content remain checked. Ordinary file fingerprints are unchanged. A legacy receipt can be reconciled with `verify-test-file-touch ALIAS --session SESSION --before-updated-at ORIGINAL-TIMESTAMP --json`: there must be one exact recorded attachment and its upload submission, no pending mutation, unchanged downloaded bytes, and complete matches to both original signed fingerprints after reversing only that timestamp. A changed name, author, grade, body, attempt, comment or other field refuses. The verifier sends no Canvas mutation.

## Expanded cleanup and recovery
```sh
uv run --project use-canvas python use-canvas/scripts/canvas.py cleanup-test example-test --session SESSION --json
uv run --project use-canvas python use-canvas/scripts/canvas.py cleanup-test example-test --session SESSION --execute --expect HASH --json
uv run --project use-canvas python use-canvas/scripts/canvas.py verify-test-cleanup example-test --session SESSION --json
```
Cleanup preflights all exact owned targets, then repeats the checks before each deletion. It removes recorded comments and replies first, then the test assignment and page/topics, personal submission attachments and finally only the newly created Test Student enrollments. Comments and replies require the exact recorded author and unchanged content. The full topic view includes newer entries over its cached view, including deletion markers. Original course inventories/order, topics, sections, existing learner enrollment and personal files must remain intact. Deleting an assignment marks only its already-recorded learner submission receipt as removed with the active parent; no claim is made that Canvas's historical attempt data was purged.

Every deletion has a durable pending marker, never retries, records its acknowledgment and verifies active absence. A discussion-entry DELETE can acknowledge success with HTTP 204 and no JSON body, as the upstream [entry controller](https://github.com/instructure/canvas-lms/blob/master/app/controllers/discussion_entries_controller.rb) implements. A readable deleted entry requires that acknowledgment plus absence from the complete active topic view. For a legacy interruption before acknowledgment was saved, read-only `verify-test-cleanup` instead requires the exact recorded entry's readable `deleted=true` marker, active-view absence, explicit moderation permission, the signed pending request and reconstruction of the prior topic fingerprint after reversing only activity metadata. It reports observed absence without claiming a retained HTTP acknowledgment. Page-specific denied readback still requires acknowledgment, permissions and complete inventory absence. New enrollment removal additionally requires an acknowledgment with `enrollment_state=deleted` and absence from the active enrollment inventory; deactivation alone refuses. Other object reads must return 404. Changed parents, partial listings, revoked permissions or unknown outcomes stop the run. `verify-test-cleanup` sends no delete and does not adopt pending creations. Continue remaining targets only through a fresh cleanup preview; success verifies the final baseline and closes the session.

An explicit submitted-file HTTP 403 can be reconciled with `verify-test-cleanup-refusal ALIAS --session SESSION --execution-file ORIGINAL-CLEANUP-OUTPUT.json --json`. The native output must report the refusal, the exact signed pending request must have one durable marker, all course test content must already be removed, and fresh reads must prove the file still matches its signed metadata and downloaded bytes. The command sends no mutation, resolves the request as not landed and retains a signed cleanup blocker; it reports the remaining file/enrollment and refuses automatic retry or new test content. This is verified incomplete cleanup. Canvas documents a [Reset Student action](https://community.instructure.com/en/kb/articles/661143-how-do-i-view-a-course-as-a-test-student-using-student-view), but it replaces the Test Student and requires separate review. Its [controller](https://github.com/instructure/canvas-lms/blob/master/app/controllers/courses_controller.rb) clears that test user’s submissions and creates a new student; the [file controller](https://github.com/instructure/canvas-lms/blob/master/app/controllers/files_controller.rb) deliberately refuses ordinary deletion of submitted files. No browser reset or file-content replacement is authorized by the original direct-delete preview.

Success requires restoration of the original active course inventory/order and learner file/enrollment baseline. Canvas soft-deletion/audit records, and the underlying automatically created Test Student user record, are not purged. Preserve the signed store, signing key and private evidence until verification completes. An unknown creation response or unresolved verification can require manual investigation; this is not a remote transaction or a guarantee against concurrent changes.

## Verification boundary
Synthetic execution covers new/existing learner access, unsupported profile reads, exact-ID setup reconciliation, text/URL/file submissions, comments, top-level/nested replies, revision restoration, announcement editing, attachment/enrollment cleanup, interrupted deletion, foreign activity and host/course/actor boundaries. The capability suite has 154 passing tests, including 24 test-cluster cases. One live test instance verified learner setup, scheduled announcement edits/restoration, an actual page revision revert, three submission attempts, a comment and both reply levels. Seven direct deletes removed all course fixtures and their active submission parent; readable entry tombstones and a delayed topic view required read-only recovery. The personal submitted file’s DELETE was explicitly refused, and the new enrollment is preserved while recovery is reviewed. Course content/order is restored; personal-file/enrollment baselines and full session closure are not. The direct-file upload confirmation correction is exercised synthetically; the interrupted live upload was already active and reconciled through reads without a confirmation request. These results do not establish production notification delivery, other institutions/roles, alternate sanitization/storage behavior or a successful reset cleanup.
