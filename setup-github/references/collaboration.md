# Collaboration runtime contract
Read this for exact issue/PR/Projects operations. Existing issue/PR bulk exports retain their open-item selection, 300-item refusal boundary and publication behavior; configured Projects exports retain their own bounds. Collaboration requests use Python 3.11+, standard-library code and the existing gh executable/account store. They require only the selected use skill and this setup sibling. No project-workflow collection is required.

## Identity, targets and transport
Pass `--repo [HOST/]OWNER/REPO` or an existing alias. `--host` is explicit; otherwise a qualified repository supplies the host, then `GH_HOST`, then `github.com`. Conflicting explicit hosts refuse. The tool reads the effective authenticated `/user` identity through gh under its actual token/environment precedence and independently resolves the repository ID. Execution requires `--actor LOGIN` or `GITHUB_EXPECTED_ACTOR`; a mismatched actor refuses and credentials are never switched or printed. Actor and repository identity are checked again before execution; actor is checked before each mutation.

The adapter uses named REST/GraphQL requests through `gh api`, with the `2026-03-10` API version. No generic endpoint/command option is exposed. Journal operations require Git for checkout/worktree and ignore/tracked-file checks; Git 2.39.5 was exercised, with `rev-parse --path-format` and `worktree list --porcelain`. gh 2.93.0's transport interface was inspected during implementation; other gh versions must support `api --hostname --method --include --input`. Server availability and permissions are separate: older Enterprise schemas/endpoints may refuse an operation, and no fallback broadens access. Error/partial GraphQL envelopes and malformed JSON never count as successful evidence.

## Preview and execution
Every mutation previews by default. The same result data renders as readable text or compact `--json`; source bodies inside either format remain untrusted data. Prefer a UTF-8 `--body-file` for durable prose to preserve literal newlines, dollar signs and backticks without shell interpolation. Omitted fields stay unchanged; an explicit empty body clears it. Metadata additions/removals preserve values outside the selected changes.

A preview returns the concrete `plan`, its `fingerprint` and an `operation_id`. The fingerprint covers actor, target, proposed requests, visible effects and relevant starting state. To execute an already authorized proposal, repeat the same command with `--execute --expect FINGERPRINT --operation-id OPERATION_ID`. Execution rebuilds the plan with fresh reads under the project journal lock and refuses a changed fingerprint. The fingerprint/flags are transport guards, not evidence of human approval. Honor existing approval within its actual scope; changed content or effects may need a new proposal. Read-then-write guards cannot eliminate races where GitHub offers no atomic condition.

Issue creation retains its existing title/body/label/assignee inputs but now requires the execution guards and verifies the created result. Existing write callers need these added flags; do not silently use the old unverified creation route. Read/export interfaces are retained.

## Project-owned journal
The operated project owns its private recovery location and ignore policy. By default, `--project CHECKOUT` (or cwd) must have a remote matching the requested host/repository. The runtime resolves the primary worktree through Git's common metadata and selects `.github/project-collaboration/` there, shared by linked worktrees. Project setup must add `/.github/project-collaboration/` to the operated checkout's root `.gitignore` before execution, leaving shared `.github/` configuration tracked. The tool does not edit project files or ignore rules. Tracked recovery files and symlinked locations refuse.

The platform adapter owns the directory mapping: GitHub uses `.github/project-collaboration/`; another forge's setup selects its corresponding platform directory and documents that location. The `project-collaboration/` subtree contains private operational records and a lock, while shared platform configuration stays outside the ignored subtree. This GitHub runtime implements the GitHub mapping.

`--state-dir DIRECTORY` explicitly selects another private location; relative values resolve against cwd, so prefer an absolute path in project configuration. A directory inside a Git checkout must be ignored and untracked. Without a local checkout, select an explicit directory; no fallback stores recovery in the installed Agent Hands checkout. Existing state directories must be owned by the current OS user with mode 0700. Records have mode 0600. POSIX file locking serializes writers across worktrees/processes; a busy lock refuses, without deleting another process's lock. Native Windows locking is unsupported; use a supported Bash/Python environment such as WSL.

If the previous default `.agent-hands/github/` exists, default journal access refuses instead of starting a fresh history. Continue using that journal with `--state-dir` to reconcile outstanding operations. To change locations, coordinate every writer, hold the existing project journal lock, preserve the complete journal and its private permissions, and update the project's ignore rule and all explicit state-directory selections together. Apply the same procedure to a project-selected custom location; never discard unresolved records or split writers across old and new locations. Migration is a separate local action, not an automatic side effect of a GitHub request.

Each step records durable uncertain intent before sending, then returned IDs and independent readback evidence. Named GraphQL operations can extract an allowlisted result ID before readback, so a later denied read retains the received identity without storing the response payload. Records contain actor/target IDs, digests, result IDs, outcomes and resource paths; no tokens or full title/body/comment/field-option/filter text are journaled. No mutation is automatically retried. An unresolved matching intent also blocks another operation ID from blindly repeating it; independent actions remain available. An intentional repeated comment uses a new operation ID after the earlier operation is verified.

Use the owning command's `recover --repo TARGET --operation-id ID` for fresh reads without resending. Setter recovery checks the selected resource; append/create recovery compares complete bounded candidate coverage, actor/content digests and IDs absent from the before-set. One unambiguous candidate is independently read back. Incomplete or ambiguous evidence stays uncertain. After inspecting a particular result, `--result-id ID` can identify it explicitly; use the issue/PR number for item creation and the REST result ID for comments/reviews. Reconciliation records local evidence only; it never submits remaining compound steps or rolls back earlier ones. Failed or unsent follow-up steps need a new concrete plan for the remaining work.

Keep unresolved records until resolved. No automatic retention/pruning or Git-tracked activity ledger is introduced. Project Workflows can configure/document the selected location; the tool itself writes the operational evidence as part of the request. Spike documents retain meaningful project outcomes and handoff context.

## Results and bounded coverage
JSON has `schema_version: 1` and an `outcome` of `preview`, `success`, `blocked`, `unsupported`, `failed` or `uncertain`. Success distinguishes applied from already satisfied for mutations. Mutation results expose `writes_sent`, per-step evidence, `partial` and remaining-step counts when applicable. A send followed by malformed output or failed readback is uncertain. A known HTTP refusal is failed; completed earlier steps remain visible. Exit codes are 0 for preview/success, 1 for known failure, 2 for refusal, 3 for uncertain or partial completion, and 4 for explicitly unsupported capability. A nonzero code does not imply zero changes.

Targeted REST/GraphQL collections default to 20 pages and 2,000 items, configurable with `--page-limit` (1–1,000) and `--item-limit` (1–100,000). Collections expose completeness and observed counts. Append/create baseline and reconciliation reads require complete selected coverage rather than claiming duplicate safety from a partial list. A PR inspection can return useful partial evidence with coverage warnings; inspect every coverage section. `read-pr --fields` selects result families to reduce agent output. `--diff-bytes` defaults to 2,000,000 bytes of returned patches; unavailable/binary/over-budget patches remain explicit. GitHub-returned patches are not a guarantee of a complete diff.

## Agent Hands handoff contract v1
| Contract part | Delivered behavior |
| --- | --- |
| Selection/capabilities | Existing setup/issues/PR/Projects skills; explicit actor/host/repository/project, documented supported operations and limits. |
| Read context | Exact issues including closed state; PR refs/OIDs, commits/files/patches, comments, reviews, checks/statuses and review threads; project/schema/view/native-enabled-flag evidence with coverage. |
| Prepare change | Default no-mutation preview, relevant baseline, exact supplied content, effects and fingerprint. |
| Execute within scope | Explicit execution guard, fresh identity/state checks, fixed transport and serialized project journal. |
| Outcome/evidence | Structured outcomes, independent readback, verified IDs, partial/uncertain recovery without blind retries. |
| Integration/history | Separate merge assessment and discussed integration command; explicit method/head, no rule bypass, no queue/auto-merge or branch deletion, optional original-commit/document checks. |

This adapter does not select project coordination mode, accept a contribution, close a spike, authorize notifications or impose one issue/PR per workstream. Those decisions remain with Project Workflows and the consuming project.

The [Projects capability](../../use-github-projects/references/collaboration.md) uses this runtime for project create/copy/link, selected field/ordered-option/view provisioning and explicit item changes. It emits verified, nonsecret lifecycle IDs for the consuming project's existing starter with enablement and native-settings attestation false. Full native workflow conditions, view grouping/sorting and Insights remain manual requirements; no second lifecycle engine or automatic hosted setup is introduced.

## Verification and source references
Run `GITHUB_TEST_PYTHON=python3.13 bash use-github-issues/tests/test-operations.sh` and the equivalent PR script from the collection root, selecting an installed Python 3.11+ executable. The integrated stateful suite is `python3.13 -B setup-github/tests/test_collaboration.py`; it exercises real subprocess previews/execution/readback against a synthetic gh executable, project/worktree state and local Git graphs. Shared legacy checks remain in `setup-github/tests/`. No live account, permissions, notification behavior, Enterprise schema, fresh-client discovery or real merge is proven by those fixtures.

Run `GITHUB_TEST_PYTHON=python3.13 bash use-github-projects/tests/test-operations.sh` for the separate Projects native CLI suite and its legacy export checks. It exercises option-ID preservation, repeat provisioning, existing configuration, stale plans, partial coverage, malformed responses, known refusals and uncertain/read-only recovery. Real project mutations and hosted close/reopen/blocking behavior require their selected live pilot; the existing consuming integration owns fresh-installation and collaborator QA.
