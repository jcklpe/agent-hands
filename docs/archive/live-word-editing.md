## Reusable capability — 2026-11-15
[Word Documents](../../use-word-documents/SKILL.md) provides headless read, paragraph-bound preview, single-dispatch replacement/save, status and independent cloud verification. [Microsoft setup](../../setup-microsoft-services/references/word-browser.md) owns initialization, ordinary browser sign-in and document-scoped startup configuration. The initial interface is a Node CLI, using the existing Microsoft Files CLI for Graph identity, metadata and downloads. There is no Graph upload in this route.

An account owns a fixed private browser directory under ignored provider state. The CLI has no normal-profile, cookie import, CDP attach or arbitrary browser-argument option. Ownership markers and an exclusive lock prevent accidental profile adoption or concurrent use. The local HTTPS bridge requires a fresh run token injected only into the owned browser, verifies the exact document, and offers no arbitrary code or enqueue endpoint. Chrome trusts the generated local certificate key only in this owned process; no system trust store is changed. Normal Chrome and native Word are independent.

Preview binds a unique match and its containing paragraph, allowing unrelated paragraphs to change. Execution rechecks the selected browser identity, document, paragraph and cloud baseline. A durable journal precedes command delivery and blocks replay. A returned Word save is followed by an independent Graph DOCX download; verification confirms the expected target paragraph, not full formatting or an atomic same-range transaction. Office.js does not provide an atomic compare-and-replace here, so concurrent changes to the same range remain a documented race. The first version refuses table edits, structural changes and revision-bearing cloud documents.

Verification: six local test cases cover identity/anchor checks, private-profile ownership/locking, dispatch replay refusal, HTTPS bridge authentication, independent DOCX verification and malformed inputs. A separate real headless Chrome test against a synthetic Office host checks read/startup/edit, an unrelated paragraph change, stale-target refusal, interrupted-save uncertainty and an independent browser remaining open. Sixteen existing skill-link tests pass, and the Word selection previews only its setup and Microsoft Files dependencies. Live read-only Graph metadata and DOCX parsing passed on the disposable target. A new private browser correctly returned `authentication_required` and closed only itself. No new document mutation or normal-browser takeover occurred.

The dedicated profile has verified the selected account after a separately authorized, narrow encrypted-cookie transfer on the same macOS user account. Chrome used its normal native credential protection; no keychain material, passwords, browser history, extensions or unrelated site sessions were copied, and the source profile stayed open and read-only. This establishes one existing-session reuse, not portable profile cloning or a guarantee against later MFA. The packaged acceptance test below verifies the combined headless-plus-open-editor route for one disposable fixture. Realistic same-range conflicts, interrupted-save reconciliation, renewed sign-in, wider deployment and Linux/Windows onboarding remain to test.

## Problem and evidence
A live, authorized replacement of a cloud DOCX returned `Locked`; after the user reported closing the document, an authorized retry succeeded and the downloaded result matched the prepared file. This establishes an observed lock conflict and successful recovery for one operation, not a guarantee that closing one client releases every possible lock. The reusable issue is that whole-file replacement competes with Office editing sessions and requires careful preservation of edits made since download. No private document content, user identities, account aliases or service identifiers belong in this spike.

Current implementation inspected on 2026-10-28:
- [Microsoft Files](../../use-microsoft-files/SKILL.md) exposes download and whole-file replacement, with preview/execute gates; there is no paragraph-editing or live Word session interface.
- [`_m365_files_replace`](../../use-microsoft-files/scripts/operations.sh) reads current metadata, requires an ETag and supplies `If-Match` when uploading the complete file. This guards the interval between that metadata read and upload. It does not bind the upload to the version originally downloaded before local editing; callers currently have to compare that baseline separately.
- [The PowerShell transport](../../setup-microsoft-services/scripts/graph.ps1) disables SDK retries for non-GET requests and reports an exception message. Preserve the no-blind-replay behavior. A reusable lock policy would need structured status/error information rather than parsing localized messages.
- Successful replacement checks remote size. A same-size response is not proof that all intended bytes, styles or concurrent edits survived; a higher-level document workflow needs content and structure readback.

## Candidate design boundaries
For file replacement, consider an explicit expected source ETag and private patch/baseline fingerprint carried from download through preview and execution. Re-read before writing; if the version changed, fetch the latest document and regenerate only the authorized edit against a uniquely resolved target. Refuse an ambiguous anchor or substantive collision. Never silently overwrite a newer file by substituting its current ETag for the approved baseline.

A confirmed lock refusal may support a short, opt-in retry policy after the lock clears, retaining the original source precondition and respecting server timing guidance when present. Bound attempts and elapsed time; stop on a changed version, permission denial, uncertain dispatch or ambiguous result. A timeout after dispatch requires readback/reconciliation before another mutation. Do not force-unlock, discard checkouts, close a user's application, create a replacement identity or remove concurrency guards to obtain success.

For a live-session route, require an explicit document/session binding and a narrow allowlist of content operations. Preview exact target content and final copy, revalidate anchors immediately before mutation, and report conflicts honestly. Use operation identifiers or equivalent reconciliation to prevent duplicate insertions after a timeout; do not assume a document index remains stable during coauthoring. Preserve surrounding styles, lists, links, human notes, comments and tracked changes. Verify local document state separately from persisted cloud state. Closing the add-in, losing the host connection or failing to save must produce an explicit partial/uncertain result.

The implementation lives in Word Documents, while Microsoft Files owns file identity, downloads and explicit transfers and Microsoft setup owns browser authentication and per-document preparation. Do not add a generic API escape hatch or make a portable provider depend on a private workspace. Keep credentials in the existing provider owner and session secrets out of logs. No browser automation, add-in installation, new grant or live test is authorized by this spike alone.

### Evidence and limits
Microsoft documents [Word web coauthoring](https://support.microsoft.com/en-us/word/coauthor-documents-anywhere). That supports using Word itself as the collaborating client; it does not establish supported, reliable headless browser automation. The [web sideloading procedure](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-office-add-ins-for-testing) describes an add-in deployment mechanism, not permission to use it in a particular tenant. Prefer a bounded add-in bridge if allowed; do not assume Office.js is callable from an arbitrary browser page without an add-in host.

The [MS-FSSHTTP overview](https://learn.microsoft.com/en-us/openspecs/sharepoint_protocols/ms-fsshttp/6d078cbe-2651-43a0-b460-685ac3f14c45) describes shared/exclusive locks and incremental file/partition synchronization using MS-FSSHTTPB. It is stronger evidence for a possible native client than WOPI host documentation, but not proof of a production-ready Word editing library, modern tenant access or conflict-safe merge semantics. Review the protocol dependencies and authentication requirements before estimating an implementation.

The [Word connector action inventory](https://learn.microsoft.com/en-us/connectors/wordonlinebusiness/) and [Office Scripts overview](https://learn.microsoft.com/en-us/office/dev/scripts/overview/excel) do not establish a Word equivalent of Excel's headless scripting route. [CSPP Plus](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/plus/overview) is a selective paid partner program. [Unattended Office requirements](https://learn.microsoft.com/en-us/microsoft-365-apps/licensing-activation/overview-unattended) specify Windows and a dedicated license; [Office automation considerations](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) explain the remaining reliability limitations.

### Restricted-tenant feasibility gates
Keep actual account identities, grants, tenant URLs and document targets in private configuration or the requesting conversation. The portable requirement is operation under an existing delegated institutional account without assuming administrator privileges.

- Local configuration and enabled file writes do not establish effective consent, target edit access, browser sign-in, add-in deployment rights or automation licensing.
- Graph authorization does not establish access to a separate SharePoint protocol resource. [Access tokens are resource-specific](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens); do not extract/replay a Graph token or borrow an application identity to bypass consent controls.
- Browser access must be checked separately. [Conditional Access session controls](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-session-lifetime) can require renewed sign-in, including MFA, for Word Online. Distinguish unattended execution during a valid session from indefinite operation without human reauthentication.
- Treat app registration, add-in deployment, new grants, automation entitlements and document/library coauthoring restrictions as independent unknowns. A missing permission should identify the specific blocker, not trigger automatic scope expansion.
- [Microsoft setup](../../setup-microsoft-services/references/account-access.md) owns delegated account access. This investigation does not authorize app-only access, standing workers or broader grants; research may compare those architectures without implementing them.

A candidate bridge would retain an immutable cloud baseline and a narrow edit intent, synchronize through a properly authenticated protocol session, apply WordCraft operations to current content, reconcile remote changes, and publish only a coherent update. It would have to preserve compatible DOCX/coauthoring metadata and handle shared leases, conflict refusal, interrupted saves and cleanup. Merely sending WordCraft's entire rewritten DOCX while holding a shared lock does not establish safe merging. The observed rewrite of styles/themes/metadata in a simple save makes broader compatibility testing necessary even where paragraph text changes are narrow. These are engineering requirements inferred from the protocol and fixture results, not implemented behavior.
