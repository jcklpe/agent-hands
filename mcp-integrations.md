# Optional MCP integrations
Reviewed 2026-10-24 against the linked vendor documentation. This is a portable sourcing and comparison catalog, not an installer, a connection manifest, or a decision to replace the CLI skills. No MCP authentication or service mutation was performed for this review. Recheck availability and advertised tools before adoption; hosted services can change independently of this repository's Git pin.

## Server, plugin, and skill are different layers
A vendor MCP server exposes a particular tool surface. A client plugin can package skills, an MCP connection, or both, and may use a different backend from the vendor's publicly documented server. A visible tool or an installed plugin does not establish account access or permission to act. This repository's CLI credentials are not automatically reusable by a connector's OAuth flow. See [OpenAI's plugin packaging model](https://developers.openai.com/plugins/build/plugins) for one client-specific example.

## Choosing deterministic restrictions
Separate three controls: the credentials' permitted resources/actions, the server or gateway's enforced operation policy, and the client's exposed tools/approval policy. A skill's guidance does not implement any of them. Disabling a tool in one client does not revoke the underlying credential elsewhere. Inspect generic request/action tools for alternate paths to the operation being restricted.

GitHub documents a server-enforced read-only filter and explicit tool exclusions. Other providers differ; inspect their actual permission/operation model rather than promising uniform controls. A requested read-only integration should be checked from its resulting tool list and enforced permissions, without attempting a destructive write as a test. CLI preview/readback behavior remains owned by its code and is not inherited by MCP tooling.

## Optional adoption procedure
1. Identify the needed operation and its current owner. Compare the selected server's actual schema with the CLI use skill, including omissions, output formats, retry behavior, and write gates.
2. Choose the exact publisher/server and supported client route from the source above. A plugin directory listing is a packaging choice, not evidence of identical backend behavior. Verify local runtime requirements for a local server; uv is unrelated to a hosted server's installation.
3. Configure only the needed connection, scopes, and operation controls within the user's authorization. Keep tokens, consent artifacts, private endpoints, account/resource IDs, and real client config outside tracked files. Never paste an existing CLI token into a guessed MCP setting.
4. Inspect discovery and identity, then perform a specifically authorized bounded read. Installation, tool discovery, and a successful authenticated read are separate verification levels. Live writes require their own target and authorization.
5. Record the selected route and client policy in the adopting environment. Do not put another user's account choices into this catalog. Preserve the CLI until the desired replacement behavior has actually been verified.

All vendor rows above are documentation-reviewed only. Local client selections belong outside the shareable collection. This file contains no automatic connections, credential templates, or required MCP dependencies.
