# Setup Workday
This capability reads, saves and submits Workday time through Chrome, either the user's everyday Chrome or a separate one with a profile kept for Workday alone, with an offline contract and preview in use-workday. Saves create unsubmitted blocks; submission is a separate command that certifies a week only after the user approves its exact preview. Read [transport status and prerequisites](references/transport.md) before attempting setup. The use skill owns the [offline CLI and draft-save engine](../use-workday/SKILL.md); this setup skill owns service transport, session binding and authorization. No unrelated provider or personal vault is required.

1. Use Python 3.9+, system IANA timezone data and Chrome 144+ on macOS; Linux is untested and Windows unsupported. Nothing beyond the standard library is needed. `use-workday`'s own CLI never contacts Workday.
2. Create the private account file `~/.agent-hands/workday/config/account.json` (or beneath `AGENT_HANDS_STATE_DIR`) from [account.example.json](account.example.json) and `chmod 600` it. Take each value from what Workday shows and have the user confirm it: the origin and tenant from the Workday address, the worker's instance ID from the `selectedItem_…` attribute beside their name on Enter My Time, the Enter My Time address path, the IANA zone the user works in with Workday's label for it from a block's details, and optionally the time-entry codes the user confirms. Never guess a worker or zone. Set `"browser"` to the user's choice: `"own"` for a separate Chrome with its own profile (step 3) or `"everyday"`, the default, for their running Chrome (step 4).
3. **Own profile (`"browser": "own"`).** When the user is at the computer, run `python3 setup-workday/scripts/workday_browser.py sign-in`: it opens a separate Chrome window at Workday, and the user signs in there themself, including any second factor, within ten minutes (`--minutes`). Once Enter My Time shows the confirmed worker the window closes. Every later command starts that Chrome without a window, needs no Allow click and quits it when done. The sign-in is kept in the profile until Workday or the identity provider ends it; a command then reports `SIGN_IN_REQUIRED`, and `sign-in` is run again. `check` shows when the profile was signed in, last worked and was first found signed out. Never type or handle the user's credentials, never copy a sign-in from another profile, and never touch Workday merely to keep a sign-in alive. Treat `~/.agent-hands/workday/chrome-profile/` as a credential.
4. **Everyday Chrome (`"browser": "everyday"`).** The user turns on remote debugging at `chrome://inspect/#remote-debugging`, signs in to Workday themself and keeps a Workday tab open in the Chrome profile to read from. `python3 setup-workday/scripts/workday_browser.py check` validates the account and reports whether remote debugging is on, without connecting.
5. `python3 setup-workday/scripts/workday_browser.py overview --from <date> [--to <date>]` lists each week's Workday hours and whether it is empty, draft, submitted, approved, mixed, unknown, without a timesheet, or unreadable, through today unless `--to` says otherwise and for at most 26 weeks. It reads the calendar only, without the cross-checks of `read`, so it answers which weeks need attention and never supports a save or submission.
6. `python3 setup-workday/scripts/workday_browser.py read --week <Monday> --out <private>/week.json` reads the week in its own background tab, which it then closes; with the everyday Chrome it first waits while the user clicks Allow. `--target <target.json>` takes `use-workday`'s v1 target instead, which must match the account; `reconcile` and `submit-preview` accept either. The output holds the validated read and observations such as classifications, payment statuses and pay-period markers; `--out` writes the snapshot owner-only and refuses a Git checkout. Pass that snapshot to `use-workday`. See [the transport reference](references/transport.md#existing-session-browser-reader) for what it checks and why.
7. Saving needs the user's explicit choice of the re-read safeguard, recorded as `"save_safeguard": "reread"` in the account file; explain the residual risk first (an edit to the same week in another tab at the moment of saving is detected afterwards, not prevented). Read the week, start from an earlier one with `use-workday propose` if it helps, run `use-workday preview` with the complete desired week, show the user the plan, and with their approval of its exact `plan_fingerprint` run `python3 setup-workday/scripts/workday_browser.py save --plan <plan.json> --approved-fingerprint <fingerprint>`. Entries must use quarter-hour times, since Workday rounds others. It saves each addition through Quick Add with the checks in [the adapter contract](references/transport.md#adapter-contract-and-the-re-read-safeguard) and reads the week back after each one. Exit 0 means saved or unchanged, 2 a clean stop before sending, 3 an uncertain save.
8. Submitting certifies the week's accuracy for approval, so it never follows from a save. `python3 setup-workday/scripts/workday_browser.py submit-preview --week <Monday> --out <private>/submit.json` reads the week, opens Workday's Submit Time panel, reads its range, hours, total and certification text, and cancels without submitting. It refuses weeks whose blocks are not all unsubmitted drafts, weeks with rounded blocks or no timesheet, a panel that names another week or other hours, and an existing comment. Show the user the range, total, every block and the certification wording; with their approval of that exact `plan_fingerprint`, `python3 setup-workday/scripts/workday_browser.py submit --plan <submit.json> --approved-fingerprint <fingerprint>` re-reads the week and panel, refuses any difference, including changed certification wording, clicks Submit and verifies every block reads Submitted. A week can be previewed at any time but submitted only from its Sunday onward, in the account's time zone. The comment stays empty. Exit 0 means submitted; 2 a refusal with nothing submitted; 3 an uncertain submission, which `reconcile` settles like an uncertain save.
9. The everyday Chrome asks the user to Allow every new connection, and each command otherwise makes its own; the own profile asks for nothing but starts Chrome each time. To share one connection across commands, start `python3 setup-workday/scripts/workday_browser.py session start` as a long-running background process and wait for its `ready` line; `overview`, `read`, `save`, `submit-preview`, `submit` and `reconcile` then go through it automatically, and `session status` and `session stop` manage it. It listens only on an owner-only Unix socket in the private Workday folder, accepts only those commands for the same account file, and ends after 20 idle minutes (`--idle-minutes`), when Chrome's connection or the session's tab is gone, or on `session stop`. With the everyday Chrome its automation banner stays visible meanwhile. While a session holds the own profile, nothing else can use it, so stop it before `sign-in`.
10. After an uncertain save or submission, run `python3 setup-workday/scripts/workday_browser.py reconcile --week <Monday>` before anything else; it settles the outcome from a fresh read, waiting ten minutes before treating absence as not applied. Then read and preview again.
11. Use normalized snapshots for local validation and preview. Keep actual worker identifiers, schedules, snapshots, plans and journals outside version control, or under the ignored `private/` directory in this skill. Verify ignores before storing anything; use owner-only directory/file permissions (0700/0600). Do not copy credentials or browser state into fixtures.
12. A documented, authorized API or MCP client would still be preferred if the tenant ever grants one. A missing personal client or empty search result is not proof that the tenant prohibits integration.
13. Respect the consumer's browser approval requirements. Implementation permission does not authorize browser use. Never extract cookies, copy profiles, guess private debugging endpoints or change browser security settings. Either browser is the user's explicit choice.
14. Do not run payroll test writes for onboarding. Each save and each submission needs the user's approval of its exact plan for real work.

## Optional global discovery
`python3 setup-workday/scripts/link-skills.py --client claude` (or `codex`) previews links for both Workday skills, and `--execute` creates them once the user wants them; see [global skill links](../setup-agent-hands/references/global-skill-links.md). Commands stay repository-relative, and no PATH link, client registration or authorization grant is created.

## Verification
The reader is verified live on macOS; Linux/WSL and native Windows remain unverified. Saving has run live on approved real work. Submission has run live only as a preview, and reconciliation of an uncertain save or submission has not run live. Offline checks: `python3 setup-workday/tests/test_workday_profile.py`, which covers the own profile and its sign-in with a stand-in for Chrome, `python3 setup-workday/tests/test_workday_submit.py`, which covers submission plans, refusals and recovery against a stand-in session, `python3 setup-workday/tests/test_workday_session.py`, which runs a session over its socket with a stand-in for Chrome, `python3 setup-workday/tests/test_workday_browser.py`, `python3 setup-workday/tests/test_workday_save.py`, which drives the save step against scripted page states, and `python3 setup-workday/tests/test_chrome_session.py`, which runs the DevTools client against a loopback stand-in and the own profile's pipe against a stand-in program. The private journal uses Unix `fcntl` locking and is not a native Windows implementation.
