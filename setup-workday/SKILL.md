# Setup Workday
This capability reads and saves Workday time through the user's own signed-in Chrome, with an offline contract and preview in use-workday. Saves create unsubmitted blocks only; nothing here submits a timesheet. Read [transport status and prerequisites](references/transport.md) before attempting setup. The use skill owns the [offline CLI and draft-save engine](../use-workday/SKILL.md); this setup skill owns future service transport, session binding and authorization. No unrelated provider or personal vault is required.

1. Use Python 3.9+, system IANA timezone data and Chrome 144+ on macOS; Linux is untested and Windows unsupported. Nothing beyond the standard library is needed. `use-workday`'s own CLI never contacts Workday.
2. Create the private account file `~/.agent-hands/workday/config/account.json` (or beneath `AGENT_HANDS_STATE_DIR`) from [account.example.json](account.example.json) and `chmod 600` it. Take each value from what Workday shows and have the user confirm it: the origin and tenant from the Workday address, the worker's instance ID from the `selectedItem_…` attribute beside their name on Enter My Time, the Enter My Time address path, the IANA zone the user works in with Workday's label for it from a block's details, and optionally the time-entry codes the user confirms. Never guess a worker or zone.
3. The user turns on remote debugging at `chrome://inspect/#remote-debugging`, signs in to Workday themself and keeps a Workday tab open in the Chrome profile to read from. `python3 setup-workday/scripts/workday_browser.py check` validates the account and reports whether remote debugging is on, without connecting.
4. `python3 setup-workday/scripts/workday_browser.py read --target <target.json> --out <private>/week.json` connects, waits while the user clicks Allow, and reads the week in its own background tab, which it then closes. The target is `use-workday`'s v1 target and must match the account. The output holds the validated read and observations such as classifications, payment statuses and pay-period markers; `--out` writes the snapshot owner-only and refuses a Git checkout. Pass that snapshot to `use-workday`. See [the transport reference](references/transport.md#existing-session-browser-reader) for what it checks and why.
5. Saving needs the user's explicit choice of the re-read safeguard, recorded as `"save_safeguard": "reread"` in the account file; explain the residual risk first (an edit to the same week in another tab at the moment of saving is detected afterwards, not prevented). Read the week, run `use-workday preview` with the complete desired week, show the user the plan, and with their approval of its exact `plan_fingerprint` run `python3 setup-workday/scripts/workday_browser.py save --plan <plan.json> --approved-fingerprint <fingerprint>`. It saves each addition through Quick Add with the checks in [the adapter contract](references/transport.md#adapter-contract-and-the-re-read-safeguard) and reads the week back after each one. Exit 0 means saved or unchanged, 2 a clean stop before sending, 3 an uncertain save.
6. After an uncertain save, run `python3 setup-workday/scripts/workday_browser.py reconcile --target <target.json>` before anything else; it settles the outcome from a fresh read, waiting ten minutes before treating absence as not applied. Then read and preview again.
7. Use normalized snapshots for local validation and preview. Keep actual worker identifiers, schedules, snapshots, plans and journals outside version control, or under the ignored `private/` directory in this skill. Verify ignores before storing anything; use owner-only directory/file permissions (0700/0600). Do not copy credentials or browser state into fixtures.
8. A documented, authorized API or MCP client would still be preferred if the tenant ever grants one. A missing personal client or empty search result is not proof that the tenant prohibits integration.
9. Respect the consumer's browser approval requirements. Implementation permission does not authorize browser use. Never extract cookies, copy profiles, guess private debugging endpoints or change browser security settings. Prefer existing-session reuse only where the host documents and permits it; a separate profile requires an explicit choice.
10. Do not run payroll test writes for onboarding. Each save needs the user's approval of the exact plan for real work; submission is unsupported.

No installation, PATH links, client registration, authorization grant, dedicated browser profile or credentials are created by this skill. Invoke the repository-relative commands directly. Global installation and fresh-client discovery are not implemented or claimed. The reader is verified live on macOS; Linux/WSL and native Windows remain unverified. Saving is tested offline only so far. Offline checks: `python3 setup-workday/tests/test_workday_browser.py`, `python3 setup-workday/tests/test_workday_save.py`, which drives the save step against scripted page states, and `python3 setup-workday/tests/test_chrome_session.py`, which runs the DevTools client against a loopback stand-in. The private journal uses Unix `fcntl` locking and is not a native Windows implementation.
