# Workday transport status
Reviewed 2026-11-16. No production transport is selected or implemented. `doctor`, live reads and `save-draft --execute` return `TRANSPORT_UNAVAILABLE`. Offline contracts and a fake-service executor are implemented; this is not a working end-to-end Workday integration.

## Discovery evidence and limits
A bounded repository/configs filename search and PATH check found the existing Workday planning pair, no `workday` executable, and no prior setup/use implementation. The existing Word browser adapter owns an Office.js-specific session and is not a Workday or ordinary-browser attachment interface. No existing implementation was imported or duplicated.

Workday's public [REST directory](https://community.workday.com/sites/default/files/file-hosting/restapi/index.html) lists Time Tracking v7. Its [developer documentation index](https://developer.workday.com/llms.txt) lists REST authentication, agent-ready MCP tools, and connecting an external agent with Workday MCP. These establish published interface families, not account entitlement or timesheet-write coverage. Attempts to retrieve the linked authentication and external-agent MCP detail pages through the research tool failed; endpoint contracts, grants and supported concurrency semantics are not verified. No authorized tenant client, credential or self-service integration route was established here. Missing client/search results do not establish a tenant prohibition. Third-party integration selection remains open; installing one without resolving authorization would not unblock access.

The available host tool description exposes `cua.getTab`, `cua.getBrowser`, and `cua.createBrowserTab` inside its managed `cua_repl`. It does not establish an importable Python/Node SDK or documented standalone CLI attachment. No host/browser API was invoked in this implementation task because browser fallback approval was pending. No cookies, private browser database, debugging endpoint, session export or security-setting change was used. Existing-session reuse, supported bounded batch execution, native login/MFA handoff, cancellation and session recovery remain unproved.

## Fixed adapter contract before enabling execution
The implementation currently supplies only `workday_core.save_draft` and the private Unix journal. A production setup-owned adapter must implement `read(target)` and `create_draft(target, entry, expected_revision=...)`, with `supports_conditional_create = True` only after proving the actual service precondition. A local flag or fake test is not evidence. Plain preflight reads cannot close the race between read and write; a browser route without an equivalent guarded save cannot satisfy this executor. Do not silently remove that protection to make a demonstration work.

`read` must independently bind tenant, worker, exact Monday-start week and timezone, return complete normalized records and all service statuses, permitted types/worktags, payroll periods, service totals, revision and save semantics. Fail on unknown layout, session expiry, MFA, missing pages, ambiguous controls, warning/validation banners or inability to verify any field. Do not turn missing UI text into an empty week. The adapter must validate worktag IDs and required combinations; the offline schema only validates string structure. Readback must be authoritative after each save, not an optimistic client form value.

`create_draft` must save exactly one planned block with explicit breaks and classifications, atomically refuse a changed revision and never certify, check in/out or submit. It must not internally retry after a lost response. Any transport error after invocation is conservatively uncertain. No arbitrary scripts/endpoints/selectors are part of the public interface. Submit, delete, edit and approval operations are absent.

Use one shared private journal directory for all clients using this integration. `Journal.guard` locks by complete target/week; different private directories would bypass local serialization. The service revision guard must still protect against other clients and human edits. Journals contain private entry data and must stay outside version control or inside an ignored private destination with mode 0700; files use 0600. Intent is flushed before mutation and retained on an uncertain effect. Interrupted processes release the OS lock but retain the intent.

Before adding a live resume/reconciliation command, establish a supported way to determine that an outstanding save has settled. Under the same lock, inspect the durable intent and perform fresh authoritative reads, verify target/status/content and distinguish saved, absent, conflicting and still-unknown outcomes. An immediate absence after timeout is not proof that a remote request will never finish. Unknown outcomes remain blocked. A settled reconciliation must record evidence privately before retiring the intent and generating a new reviewed plan. No recovery command or automatic journal deletion is exposed today. Partial saves do not authorize deleting records as rollback.

## Remaining acceptance gates
- Verify a supported authorized transport from the actual CLI runtime and record exact source/version, scopes, session ownership and platform.
- Prove complete read-only retrieval on an authorized week; independently confirm identity, timezone, classifications, periods, totals and all statuses.
- Verify conditional draft-only persistence, authoritative readback and durable settled reconciliation under separately authorized real work, including conflict/expiry/cancellation behavior. Do not create disposable payroll data to test.
- Verify client installation/discovery separately. Current commands are repository-relative only; no global links or PATH installation were performed.
- Human QA and Linux/WSL/native Windows remain outstanding. The current executor journal uses Unix `fcntl`; Windows requires a separately tested lock implementation. No token/cost reduction is measured.
